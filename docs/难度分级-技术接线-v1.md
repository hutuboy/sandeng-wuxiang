### 1.2 导出 API 契约（终裁口径）

| 导出 | 类型 / 签名 | 语义 | 是否可变 |
| --- | --- | --- | --- |
| `VERSION` | `string` 常量 | `'difficulty.v1'` | 冻结 |
| `SCHEMA_VERSION` | `string` 常量 | `'sandeng.difficulty.v1'`，**只作 `cs.difficulty.configId`**，不写进存档 `session` | 冻结 |
| `PARAM_STATE` | `string` 常量 | `'READY'`；**仅用于自检 / 构建期门禁，不进运行时分支**（§6） | 冻结 |
| `IDS` | 有序 `string[]` | `['novice','basic','intermediate','advanced']` | 冻结数组 |
| `LABELS` | `Object<id, string>` | id → 中文名（取自设计案 §3.1） | 冻结 |
| `DEFAULT_TIER_ID` | `string` | `'basic'`（初级），全链路唯一回落目标；**严禁用 `IDS[0]`**（那是 `novice` / 新手级） | 冻结 |
| `CONFIG` | `Object<id, TierConfig>` | 每档 `{ id, label, nights }`，`nights[3]` 为 `derive()` 生成并冻结的只读派生视图 | 深冻结 |
| `normalize(raw)` | `→ id` | **唯一归一 / 回落入口**：合法 id 原样返回；非法 / 缺失一律回落 `basic`，**永不返回 `null`、永不抛异常**；禁止模糊匹配 / `parseInt` / 大小写宽松 | 纯函数 |
| `paramsFor(tierId, night)` | `→ NightParams` | 按冻结的 `nights[]` 取该夜派生视图，**冻结返回**；`night` 夹取到合法夜次 | 纯函数 |
| `apply(id, state)` | `→ cs.difficulty` | **生成 `cs.difficulty` 的唯一入口**：返回**普通对象（不冻结）**，便于 `JSON.stringify` 进存档；带 `configId`；不修改入参 `state` | 纯函数 |
| `get(id)` / `label(id)` / `validate(id)` / `validateConfig()` | 既有 API | `get()` 非法回落 `basic`、永不返回空；`validateConfig().filled` 在数值填满后须为 `true` | 纯函数 / 冻结结果 |

> **禁止复用 `resolve` 名称**：v1 初稿的 `resolve(tierId, night) → NightParams` 与骨架 `resolve(state) → id|null` 同名不同参，接线必错。终裁**两边都改名**：归一用 `normalize`，取参用 `paramsFor`，`resolve` 已从模块移除。
>
> **单一入口**：所有运行时消费方一律 `normalize(session.difficultyTier)` 现算，禁止各模块各自写 `if (!tier) ...`；`apply()` 是 `cs.difficulty` 的唯一产出路径，`director.difficulty()` 不得自行组装对象。

### 1.3 数据结构（配置层 / 运行层分离）

```
配置层（唯一数值来源）
  TIER[id]  = 设计案 §3.2 的跨夜恒定契约值（13 项）
  D₀(n)     = 设计案 §1.1 的现状三夜基线（跨档恒定）
  derive(tier, night) : 纯函数，按设计案 §5.2 公式从 TIER + D₀(n) 派生
                        → 在模块初始化时生成并冻结 CONFIG[id].nights[3]

运行层（消费点）
  cs.difficulty = apply() 产出的普通对象，13 字段：
    保留 7（名称一个不改）：
      night / lamps / clueCount / evadeBoost / redHerring / allowFlee / temperature
    新增 6（逐字采用设计案 §3.2）：
      trustMaskBelow / tensionLeaveAt / fleeSuspicionAt
      suspicionGainScale / chainMinForFullCredit / endingBestTrust
    可选元信息（未知键不破坏老存档）：tier / rhFrom / fleeFrom / configId
    派生量不落字段：endingBestChain = clueCount * 3（在 game.js 现算）
```

| 契约要点 | 说明 |
| --- | --- |
| **不硬编码派生终值** | 裁决单 §3「实现策略裁决（v1.1 修订）」：运行时**只存 13 项契约值 + `D₀(n)`**，由 `derive(tier, night)` 按 §5.2 公式派生并冻结 `nights[3]`；**禁止**把设计案 §5.3 的 12 组派生终值硬编码进运行时配置 —— 否则同一数值会在契约表 / 派生表 / 运行时配置三处各存一份，违反「同一事实只有一个载体」 |
| **事实分层** | ① 运行时配置 = 13 项契约值 + `D₀(n)`；② `derive()` = §5.2 公式的纯函数实现；③ §5.3 的 12 组派生终值 = **QA 判据①的写死期望值**，只存在于 `tools/qa/difficulty-matrix-oracle.cjs`，不进运行时、不进配置。三者角色互不重叠 |
| **字段名不改名** | `npc.js` / `director.js` / `ui.js` 读取 `game.cs.difficulty.*` 的既有 7 键一个都不能改；新增 6 键由接线点读取 |
| **配置层 ≠ 运行层** | `rhFrom` / `fleeFrom` 是配置层起始夜，**必须在 `derive()` 内换算成 `redHerring = (n >= rhFrom)` / `allowFlee = (n >= fleeFrom)` 两个布尔量**再进 `cs.difficulty`；`npc.legalMask()` 读的是 `allowFlee`，切勿把起始夜本身塞进运行期对象，否则老版读新档失效 |
| **未定义槽位一律删除** | v1 初稿与骨架里 `nightCount / guestCount / tensionRate / trustRate / lieRate / memoryWeight / evidenceWeight / scoreMultiplier / hintLevel / lampCount / aiTemperature` 等**本规格未定义或无消费点**的槽位**删除，不得填数**；「三夜三客」是案件生成器硬约束，不是难度旋钮 |

  var CONFIG = {};
  IDS.forEach(function (id) {

    for (var n = 1; n <= D0.length; n++) nights.push(derive(id, n));

    return t.nights[toNight(night) - 1];                  // 冻结返回

    var p = paramsFor(id, state && state.night);
    var snapshot = shallowCopy(p);                        // 普通对象，可 JSON.stringify
    snapshot.configId = SCHEMA_VERSION;
    return snapshot;
  }
  function get(id) { return CONFIG[normalize(id)]; }
  function label(id) { return LABELS[normalize(id)]; }
  function validate(id) { return IDS.indexOf(id) >= 0; }

  var Difficulty = deepFreeze({

### 1.5 只读冻结策略

| 层级 | 处理 | 理由 |
| --- | --- | --- |
| `IDS` / `LABELS` / `CONTRACT` / `D0` / `CONFIG` / 每个 `TierConfig` / `nights` 数组 / 每个 `NightParams` / `SD.Difficulty` 自身 | 递归 `deepFreeze` | 单层 `Object.freeze` 挡不住 `CONFIG.basic.nights[0].lamps = x`；必须深冻结 |
| `nights[3]` | 由 `derive()` 在初始化时**生成后立即冻结**，无独立编辑权 | 派生视图不是第二份事实，不得手工录入 |
| `apply()` 返回值 | **不冻结**，普通浅拷贝 | `cs.difficulty` 要随 `game` 进 `JSON.stringify` 存档；同时保证「任何消费方都改不到全局配置」 |
| 消费方约束 | 全链路只读 | `'use strict'` 下写冻结对象会抛 `TypeError`，正好作为「误接线」的早期暴露（§7.2-4） |
| 禁止 | 模块级可变单例、缓存当前档位、`window.currentTier` | 见 §4.1「无新增全局可变状态」 |

### 1.6 版本键与档位 id 枚举

- **版本键**：`SCHEMA_VERSION = 'sandeng.difficulty.v1'` **只作 `cs.difficulty.configId`**；`VERSION = 'difficulty.v1'`、`PARAM_STATE = 'READY'`。它们与 `sandeng.state.v1`（只读快照）、`sandeng.save.v2`（持久化信封）、`sandeng.agent.trace.v1` / `sandeng.selftest.v1` / `sandeng.defect.v1` 各自独立，不得互相借用。
- **档位 id 枚举**：`IDS = ['novice','basic','intermediate','advanced']`（有序；顺序即封面展示顺序与递进顺序）。ASCII 小写、精确字符串相等，可直接进 URL 查询串 / JSON / DOM `data-*`；中文名只在 `LABELS` 出现一次。
- **默认档**：`DEFAULT_TIER_ID = 'basic'`（初级）。**严禁用 `IDS[0]`**。所有「缺失 / 非法 / 版本不匹配」路径统一收敛到此。
- **`PARAM_STATE` 的边界**：只卡发布 / 自检 / 构建期门禁，**不进运行时分支**（裁决单 §5：反对为门禁硬造运行时降级）。运行时守卫只保留「`SD.Difficulty` 是否存在」一条（§5.4）。
- **无迁移器**：本轮只有 v1，**不做跨版本存档迁移**；老档判「字段缺失」即回落 `basic`，未来升版另开变更单。

## 3. 存档兼容方案

### 3.1 两个易混的「存档」

| 名称 | 实际位置 | 生产者 / 消费者 | 本规格处理 |
| --- | --- | --- | --- |
| **持久化存档信封** `sandeng.save.v2` | `localStorage` 键，值 `{ v, session, game, selected, tone, ended }` | `main.js` `save()` / `load()` / `continueRun()` | 难度字段加在**信封内 `session`**（§3.2） |
| **只读状态快照** `sandeng.state.v1` | `Game.snapshot()` 的 `schema` 与返回对象 | `SANDENG_API.getState()`、`Agent.getState()`、`App.autoTrace.initial/final`、UI 文案 | **逐字段不变**（§3.5） |

### 3.2 字段加在哪一层

```
sandeng.save.v2 信封
├── v                     ← 不动（保持现状值）
├── session               ← 【新增字段落在这一层】
│   ├── seed / night / totalScore / nights   ← 现状字段，不动
│   └── difficultyTier: <id 字符串>          ← 唯一新增，可选
├── game                  ← 形状不动（cs.difficulty 随 game 一起序列化）
├── selected / tone / ended                  ← 不动
```

选 `session` 层的理由：① `session` 是 run 级（跨三夜共享），对应「档位在 run 内锁定」；② `save()` 已整体序列化 `session`，**信封顶层与 `v` 不用改**，老版忽略未知键天然兼容；③ **不写进 `game`** —— 每夜 `cs.difficulty` 是派生值，再存 id 会出现两个真相源；④ **不写进 `sandeng.state.v1`** —— 快照是对外只读契约；⑤ **不另开存储键** —— `file://` 下 `localStorage` 可能不可用，单键才能与内存态兜底一致。

> **无新增全局可变状态**：不新增 `window.*` 变量、不新增模块级可变单例、不在 `App` / `UI._cache` 缓存 `tierId` 副本。档位只是 `App.session` 记录里的**一个数据字段**；各处一律 `normalize(App.session.difficultyTier)` 现算（纯函数、零成本），避免双真相源。

### 3.3 回落规则（`normalize()` 单一入口）

| 输入 | 输出 |
| --- | --- |
| `undefined` / `null`（老存档无此字段） | `basic` |
| 合法 id 字符串 | 原样返回 |
| 未知字符串 / 数字 / 布尔 / 数组 / 对象 / 大小写不符 / 首尾空格 / 空串 / 中文 / URL 残留 / 原型键 | `basic` |

约束：白名单用 `IDS.indexOf()`，**天然挡住原型链键**；不抛异常、不写回存档、不修改入参、非法值不得写进 `session` / 存档 / seed。**缺失 / 默认回落不提示**；**非法 id 提示恰好一次**（`UI.toast('难度未识别，已按初级开局')`）。本轮**不做跨版本迁移**。

| **`?guide=1` 引导复跑** | URL 同时带任意 `difficulty` | `boot()` | **忽略 URL 档位**，固定 `basic` + 第 1 夜 | 设计案 §6.2，保护引导的 6 盏灯基线 |
| **`?seed` 复现入口** | URL 只带 `?seed=<s>&night=<n>` | `boot()` → `newRun()` | 不指定档位 → 回落 `basic` → 与 v1.1.0 一致 | §3.6 硬约束 |
| **`file://` / 隐私模式** | `localStorage` 读写抛错 | `save()` / `load()` / `continueRun()` | 档位随 `App.session` 留在**内存态**；`continueRun()` 的 `(!s \|\| !s.game) && App.game` 分支（`L82–89`）继续可用并同样执行补齐；**不得改动这两处兜底逻辑** | 现有 try/catch + 内存态分支 |
| **存档损坏** | `session` 非对象 / JSON 解析失败 | `load()` | 现有 `try/catch` 返回 `null`，按无存档处理；非法 id 从不写进 `session` | 现有逻辑不改 |

### 3.5 `sandeng.state.v1` 快照不变契约

`Game.snapshot()` 的 `schema` 字符串与返回字段集**逐字段保持不变**。因此 `SANDENG_API.getState()`、`Agent.getState()`、`App.autoTrace.initial/final` 输出形状不变；关于页与自动试玩轨迹弹窗引用 `sandeng.state.v1` 的文案不必改；「档位可观测」只通过 **`SANDENG_API.getDifficulty()`**、**UI 顶栏 `#tb-tier[data-difficulty-tier]`**、**`App.session.difficultyTier`** 三通道暴露，不进快照。若将来确实需要把档位带进对外状态，**必须另起 `sandeng.state.v2` 并做双版本兼容**，本版不做。

### 3.6 `?seed` 逐位复现契约（本轮最高风险）

**（1）默认档必须等价于现状曲线（硬约束，已闭环）**

`?seed=<s>&night=<n>` 不带 `difficulty` 时回落 `basic`。设计案 §3.3 恒等性契约与 §5.4 极值可达性实测已确认：默认档叠加分量恒等、六个绝对阈值等于现有字面量，故 `D(n, basic) ≡ D₀(n)` 对三夜全部成立 → 同一 seed 生成同一案件，历史分享卡 / 创作手记运行记录 / 200 组种子基线 / QA 回归基线全部不失效。

**（2）RNG 盐串冻结**

以下盐串**一个字符都不许改**，更不许把 `tier` 拼进去（否则既有 `?seed=` 分享链接全部作废）：

| 盐串 | 位置 |
| --- | --- |
| `seed + '\|night' + night + '\|try' + attempt` | `director.js` `buildCase()` |
| `seed + p.name + night` → `C.hashStr(...)` | `director.js` `buildCase()` 的 `portraitSeed` |
| `cs.seed + '\|n' + cs.night + '\|t' + game.turn + '\|' + salt` | `npc.js` `rngFor()` |
| `seed + x.id + mainTopic` | `director.js` 红鲱鱼分支（独立 RNG） |

**（3）档位参数会改变 RNG 消费 —— 已更正的事实**

`clueCount` 与 `redHerring` **确实会改变 `buildCase()` 主 `rng` 的消费序列**（设计案 §6.4 实测）：`clues.map()` 中每条物证都会额外 `rng.pick(topic.values)`（`director.js` `L80–88`），物证数不同则主 RNG 消耗次数不同；红鲱鱼分支位于 `guests = picks.map(...)` 回调**内部**（`director.js` `L111–114`），会在后续客人生成之前消耗主 RNG。因此：

> **「同 seed + 不同档 → 不同案件」是预期行为，不是缺陷。** v1 初稿中「`shuffle(...).slice(...)` 不额外消耗 RNG」「红鲱鱼分支在客人数据生成完毕之后才消耗主 RNG」「`clueCount` 改变不影响 RNG 消耗序列」三处陈述**与实测不符，已全部删除**。

**（4）复现主键与 `params()`**

复现主键由 `(seed, night)` 扩为 **`(seed, night, tier)`**：

- `basic`（默认）：两字段与 `D₀(n)` 完全相同 → 旧链接 / 旧存档 / 旧自检**逐字节复现**；
- 其余三档：分享与复跑链接**必须带 `difficulty=<id>`**，`shareText()` 追加难度名（§2）；同一三元组必得同一结果；
- `?seed=X&night=N` 不带 `difficulty` → 回落 `basic`，与 v1.1.0 一致。

`params()` 已通用解析任意查询键，**无需改动**；`?guide=0/1`、`?autopilot=1`、`?seed`、`?night` 的解析与分支顺序不变。`?guide=1` 强制首夜路径必须走默认档，引导层契约（`guide.js` 声明「禁止读写 `sandeng.save.v2`、禁止改灯数与证词」）不受影响。

**（5）浮点漂移**：温度倍率结果统一取两位小数后再入公式（设计案 §5.2），避免跨浏览器 / 跨 Node 的 `softmaxSample` 末位漂移；夹紧在生成前完成，夹紧不得改变 seed。

### 4.2 按平台分节

**P0 · 魔搭 Static 创空间（HTTP 静态托管）— 必须**：新增文件随仓库静态发布，无需构建；UTF-8 编码，经典 `<script>` 而非 `type="module"`；不引入外部资源、鉴权、Cookie、服务端时钟；页面版本号与档位表同步发布（建议）。平台规则与缓存行为可能随时间变化，**以魔搭创空间官方文档为准**。

**P0 · `file://` 本地双击 — 必须**：全部脚本保持经典 `<script src>` 顺序加载；`localStorage` 可能不可用，`save()` 的 try/catch 与 `continueRun()` 的 `App.game` 内存分支是唯一兜底、**不得改动**；档位随 `session` 走内存态；`location.search` 在 `file://` 下可用，`?seed` / `?night` / `?guide` / `?difficulty` 解析不变；不引入 `IndexedDB` / `File` / `cookie`。

**P1 · 其他静态托管 — 必须 / 建议**：必须 —— 同源即可运行，不假设登录态、CDN 重写、服务端路由；建议 —— 启用 CSP 时用 `'self'`，本模块无需 `'unsafe-eval'`。

**P2 · 商店 / 主机 / 移动端封装 — 未排期，暂不预审**：建议 —— 当前不设计、不预审。若未来要封装，需另起架构评估（离线包、隐私与权限、分级、计时器权限、内购与分成），并按「引擎中立」维度重评技术栈。**平台规则（分成比例、认证项、商店审核要求）随时间变化，以各平台官方文档为准**，本文件不写死任何规则结论。

### 4.3 为何「时间限制」应以行动点实现

结论：**档位的紧迫度只能由 `lamps` / `lampsLeft` 这套既有行动点表达，禁止引入 `deadline` / `timer` / `setInterval` / 墙钟倒计时 / `turnCap`**。理由：

1. **确定性是产品契约**：`?seed` + 动作序列（现扩为三元组）是当前唯一输入；`core.js` `RNG`、`npc.js` `rngFor()`、`director.js` 案件生成共同保证逐位复现。墙钟时间不可复现，一旦入状态，`SANDENG_API.getState()`、`App.autoTrace`、创作手记运行记录、分享卡全部失去可比性。
2. **机制已经存在且够用**：`game.js` `dispatch()` 在 ASK / LISTEN 上 `lampsLeft--`，`lampsLeft <= 0 → conclude(game, 'lamps')` 自动结算；`ui.js` `lampsHtml()` 可视化剩余灯；`director.js` `solve()` 已有 `enough: cs.lamps >= cost` 的**行动点充足性约束**。「时间限制」等价于「收紧初始灯数」，只需把 `lamps` 配成档位参数，**零新机制**；`game.turn++` 与 `lampsLeft--` 同一次调用同步发生，**回合上限 ≡ 灯数**，无独立回合计数。
3. **合规硬约束**：无服务端时钟、无后台计时 → 无额外权限申请、无平台审核项；静态托管下跨设备 / 时区 / 标签页挂起 / 系统休眠的墙钟行为不一致，属不可控外部输入。
4. **无新增全局可变状态**：计时器必然引入 `startAt` / `deadline` / `timerId` 这类可变状态与清理逻辑，与 §4.1 冲突，也给 `file://` 兜底增加一条必须同步的内存态。
5. **体验与可访问性**：回合制推理游戏，玩家思考时长不应被惩罚；现有 `prefers-reduced-motion` 处理（`ui.js` `initCanvas()`）已体现对节奏的照顾。
6. **过度工程警戒**：引入计时器还要处理暂停 / 后台 / 存档恢复时的剩余时间计算，对一人 / 小团队是纯维护负担，收益为零；且会与 `conclude(game,'lamps')` 形成双终止条件，破坏灯尽自动结算的唯一性。

> 若设计案参数中出现「时限」类字段，**不得**按字面实现为墙钟计时；建议映射为「初始灯数」或「每轮行动点消耗」，由 game-design-director 与 team-lead 确认映射后再接线。

### 4.4 平台优先级与推进顺序

| 优先级 | 平台 | 本轮动作 |
| --- | --- | --- |
| P0 | 魔搭 Static 创空间 | **现在就要做**：脚本引入 + 全链路接线 + 兼容矩阵 + 验收门禁 |
| P0 | `file://` 本地双击 | **现在就要做**：本地双击回归、`localStorage` 不可用时档位仍随内存态存活 |
| P1 | 其他静态托管 | **到那一步再说**：同源即可，无需代码改动，仅在真正部署时做一次冒烟 |
| P2 | Steam / 主机 / 移动端商店 | **未排期、不预审**：若立项，另起引擎中立选型与平台合规评估 |

**现在就要做**：§2 九项缺项销项、§3.4 兼容矩阵断言、§4.1 合规扫描、§6 门禁。**到那一步再说**：多版本 `SCHEMA_VERSION` 迁移链、`sandeng.state.v2`、档位热更新 / 远程配置、商店封装、引擎选型重评 —— 均不制造为当前需求。

### 5.3 模块加载顺序与 `SD` 全局对象的关系

`SD` 由 `core.js` 以 `var SD = (g.SD = g.SD || {})` 创建，其后每个模块在**自身 IIFE 执行时**把子模块挂到 `SD` 上。`main.js` 在 IIFE 顶部一次性取 `SD.Core / Game / NPC / Agent / UI`，随后 `boot()` 才执行。因此：

| 顺序 | 脚本 | 与配置模块的关系 |
| --- | --- | --- |
| 1 | `core.js` | 必须先加载，否则 `SD` 不存在 |
| **2** | **`difficulty.js`（插入点）** | 挂载 `SD.Difficulty`；**必须在 `director.js` 之前** |
| 3 | `director.js` | IIFE 顶部取 `SD.Core`；运行时调 `SD.Difficulty.apply()` |
| 4 | `npc.js` | 运行时读 `game.cs.difficulty`，**不直接读 `SD.Difficulty`** → 无需调整顺序 |
| 5 | `game.js` | 顶部取 `SD.Core / Director / NPC`，此时已就绪 |
| 6 | `agent.js` | 同上 |
| 7 | `ui.js` | 顶部取 `SD.Core / NPC / Game` |
| 8 | `guide.js` | 不改 |
| 9 | `main.js` | 最后加载，`installAPI()` 才能挂上 `getDifficulty()` |

**硬规则**：新模块**只允许**挂载一个冻结属性 `SD.Difficulty`；禁止覆盖 `SD` 本身、禁止改写其他模块属性、禁止在加载时读取其他 `SD.*` 模块（避免顺序耦合）；用经典 `<script src="js/difficulty.js"></script>`，**不得**用 `type="module"`。若脚本被放到 `main.js` 之后，`boot()` 已执行、`installAPI()` 已跑完，`SANDENG_API` 会缺 `getDifficulty()` 且封面控件渲染时取不到枚举 → 直接判接线失败。

### 5.4 「骨架尚未被 `index.html` 引入」的影响与渐进接线

`js/difficulty.js` **终版 v1 已落盘**，但 `index.html` 的脚本列表仍为原有八个、**尚未引入**。因此：

- 本文件 §1.4 的代码块是**规格示意**；本文档不创建运行时文件、不改 `index.html`；
- 实施第 0 步是「插入 `<script>`」，**在此之前 §2 中所有依赖 `SD.Difficulty` 的接线一律视为「缺失 / 未接线」**；
- 为支持分步上线，`director.difficulty(night, tierId)` 必须保留一条守卫：**`SD.Difficulty` 未加载时原样回落现有三夜曲线**。这样「只加脚本、尚未改任何消费方」的中间态**行为完全不变**，可先发一次空转版本再逐模块接线；
- `main.js` / `ui.js` 同理：取不到 `SD.Difficulty` 时，封面控件与 `#tb-tier` 不渲染或显示默认档文案，**不得抛异常**；
- **运行时守卫只此一条**，`PARAM_STATE` 不进运行时分支（§1.6 / §6）。

允许主程序修改的只有：按裁决单 E 的接线点改 `director.js` / `game.js` / `npc.js` / `main.js` / `ui.js`，`index.html` 增一个 `<script>` 与封面 / 顶栏控件，`assets/style.css` 增四档单选样式。**禁止**改动 `Game.snapshot()` 形状、`core.js` 的 `RNG`、各 RNG 盐串、`save()/load()` 兜底分支、`guide.js` 引导契约、`Agent.selftest()` 的 6 条基线语义、以及 `SANDENG_API.version`。

## 6. 验收门禁（均按「门禁卡点」归类，不造运行时降级）

> **归类依据（必须写明）**：难度配置是**加载期即确定的纯数据**，运行时没有可降级的资源维度（不像帧率 / 内存可动态下调）；在运行时偷偷改档位只会破坏确定性与 `?seed` 复现，属于「为门禁硬造运行时降级」，是过度工程。因此下列条目一律按**门禁卡点**入表，卡在发布 / 验收环节，写清阈值、触发点、判定人与后果。本轮未引入渲染 / 内存 / 网络新负载（纯数据模块常驻体量可忽略），**不新增性能预算条目**，现有性能预算不变。

| 门禁项 | 具体阈值 / 触发点 | 卡在哪个环节 · 谁判定 | 不达标后果 | 归类依据 |
| --- | --- | --- | --- | --- |
| **配置冻结性门禁** | 加载后 `Object.isFrozen(SD.Difficulty) === true`，且 `IDS / LABELS / CONTRACT / D0 / CONFIG / 每个 TierConfig / nights 数组 / 每个 NightParams` 递归全部为 `true`；`nights[3]` 由 `derive()` 生成且无独立编辑权；`apply()` 返回值为**不冻结**普通对象 | `index.html` 脚本引入后的冒烟检查；**主程序**判定 | 不得进入下游接线，先修深冻结 / `derive()` 实现 | 纯数据在加载期一次性确定；运行时无降级动作，改值即破坏确定性 |
| **行动点充足性 / 极值可达性门禁** | 四档 × 三夜共 12 组派生值全部落在设计案 §1.3 合法区间；`lamps >= 每夜客人数`（`solve().enough`）、`clueCount` 落在词库允许范围恒成立；`cs.solvable === true`，`solverTrace` 无 `unique:false` / `enough:false`、无重掷兜底 note；用 `tools/qa/difficulty-matrix-oracle.cjs` 独立复算 §5.2 公式与运行时 `derive()` 输出**逐项互证** | QA 验收阶段（独立 oracle，不反读实现）；**QA-lead** 判定 | 该档位参数**不得合入**，退回 design-director 调参 | `generate()` 全失败时返回 `last` 并标记 note，案件不可解且 `?seed` 结果漂移；运行时无法自动补救，只能在合入前阻断 |
| **快照 / 复现不变门禁** | 默认档下固定 seed 跑同一动作序列，`JSON.stringify(SANDENG_API.getState())` 与基线**逐字节一致**；`Game.snapshot()` 字段集与基线完全一致（无新增 / 删除键）；既有 `selftest 6/6`、`browser-smoke` 0 报错、`guide-smoke 60/60`（含负向计数全 0）全部通过 | 回归比对环节；**QA-lead** 判定 | 回滚任何对 `snapshot()` 的字段改动；或按 §3.6 保留默认档恒等曲线 | 快照是对外只读契约，加字段即破坏 `getState()` / `autoTrace` / 分享卡；无运行时降级路径 |

> **制作人裁决单 §7 六条硬约束并入本表一并执行**：① 默认档逐字节恒等 v1.1.0；② 默认档下 `?seed&night` 逐位复现；③ `sandeng.state.v1` 快照不改、老存档回落可续玩；④ 回归三套既有门禁；⑤ 12 组参数落在合法区间且 `lamps >= 每夜客人数`；⑥ 非法 id 不得写进 `session` / 存档 / seed。**门禁登记写入 `docs/交付清单.md`「复跑命令」段**（裁决单 §8）。
