## 1. 裁决 A · 唯一规格来源

**`docs/难度分级-设计案-v1.md` 为难度域唯一规格来源**：档位 id、13 项契约参数、合法区间、叠加公式、12 组派生终值表、判定规则，全部以该文件为准。其他文档**只引用、不复述、不另立一份难度表**。

### 关于我自己先前裁决的修订（如实记录）

我在设计案落盘前发过一条裁决，称「字段必须逐字采用 `director.difficulty(night)` 现有 6 字段，`trustRate / … / hintLevel` 等零消费点一律不进参数终值表」。**该裁决基于不完整的检索**：当时只搜了 `game.cs.difficulty.*` 的动态读取，未识别到「硬编码字面量本身就是要被参数化的消费点」。

核实后修订为：

- 原 6 个运行期字段（`lamps / clueCount / evadeBoost / redHerring / allowFlee / temperature`）**名称一律保留**，是 `npc.js` / `director.js` / `ui.js` 的既有读取键，不得改名；
- 设计案 7 项绝对阈值中，除 `endingBestChain` 为**派生量**（`= clueCount × 3`，不设独立数值）外，其余 **6 项确有真实消费点，全部纳入**；
- 骨架 `PARAM_KEYS` 里 `nightCount / guestCount`（3 夜 3 客是案件生成器硬约束）与 `tensionRate / trustRate / lieRate / memoryWeight / evidenceWeight / scoreMultiplier / hintLevel`（现有 `js/` 零消费点）**一律作废**，不得凭空接线。

## 3. 裁决 C · 运行期字段集与结构

`cs.difficulty` 是**唯一消费点**（`npc.js:66/79/96/160/167/179/273`、`director.js:149/166`、`ui.js:338`）。字段集定为：

| 类别 | 字段 | 说明 |
|---|---|---|
| 保留（不得改名） | `night`, `lamps`, `clueCount`, `evadeBoost`, `redHerring`, `allowFlee`, `temperature` | 现有 7 字段，`director.difficulty()` 返回结构完整保留 |
| 新增（6 项阈值） | `trustMaskBelow`, `tensionLeaveAt`, `fleeSuspicionAt`, `suspicionGainScale`, `chainMinForFullCredit`, `endingBestTrust` | 字段名逐字采用设计案 §3.2；**不用**架构的 `trustGate / tensionGate / suspicionGate`（作废） |
| 派生（不进配置） | `endingBestChain = clueCount * 3` | 在 `game.js` 现算，避免第二份事实 |
| 可选元信息 | `tier`, `rhFrom`, `fleeFrom`, `configId` | 便于 AI 面板 / 调试；未知键不破坏老存档 |

**结构裁决**：`CONFIG[id].nights[]`（长度 3，下标 = 夜次 − 1），每元素为上述字段的一组运行期终值。骨架的扁平 `CONFIG[id].params` **作废**。

**实现策略裁决（v1.1 修订，采纳 lead-programmer 的阻塞请示建议 2）**：运行时**只存 13 项跨夜恒定的契约值 + 现状三夜基线 `D₀(n)`，用纯函数 `derive(tier, night)` 按设计案 §5.2 公式派生**，**禁止**把 §5.3 的 12 组派生终值硬编码进运行时配置。

- **修订理由（如实记录）**：我初版裁决为「直接查表」，理由是规避公式实现 bug；但硬编码 12 组派生终值会让「同一数值」在 §3.2 契约表 / §5.3 派生表 / 运行时配置三处各存一份，违反「同一事实只有一个载体」铁律，且设计案 §5.3 原文明确其用途是**给 QA 当写死期望值**。主程序建议更严谨，采纳。
- **事实分层**：① 运行时配置 = 设计案 §3.2 的 13 项契约值（唯一数值来源）+ §1.1 的 `D₀(n)` 现状三夜曲线；② `derive()` = §5.2 公式的纯函数实现；③ 设计案 §5.3 的 12 组派生终值 = **QA 判据①的独立期望值**，写死在验收脚本里，不进运行时、不进配置。三者角色互不重叠，不构成第二份事实。
- **恒等性自证**：`basic` 的 6 个叠加分量全 0 / ×1.00、7 个阈值逐一等于现有字面量 ⇒ `derive('basic', n)` 输出逐字段 ≡ `D₀(n)`，无需特判。
- **舍入边界**：主程序实测 `1.15×0.90 = 1.035`、`1.15×1.10 = 1.265` 恰落在 `.5` 舍入边界，JS `Math.round(x*100)/100` 下得 `1.03 / 1.26`（银行家舍入不致 1.04/1.27）。**`derive()` 必须显式实现 §5.2 的「取 2 位」语义并统一一处**，不得各处自行 `toFixed`；QA 用同一组边界值做已知答案自验。

### 3.1 追认主程序的两处施工解读（终裁补充）

主程序在实施中发现本单 §3 初版「`nights[]` 每元素为运行期终值」与 §3 v1.1 修订「禁止把 §5.3 的 12 组派生终值硬编码进运行时配置」存在文字张力，主动上报两处解读。**均予追认，写入终裁**：

1. **`CONFIG[id].nights[3]` 是只读派生视图，不是第二份事实**：保留 `nights[3]` 结构以满足 `paramsFor(tierId, night)` 的 O(1) 取参，但每元素由 `derive(id, n)` 在模块初始化时按 §5.2 公式计算生成后深冻结，**无独立编辑权**。唯一数值录入处只有 12 项契约值 + `BASE_NIGHTS`（D₀(n)）。该解读比本单原表述更严谨，采纳。
2. **`PARAM_KEYS` / `CONTRACT_KEYS` / `DERIVED_KEYS` 分层**：`PARAM_KEYS` 取裁决 C 的 **13 个运行期字段名**（7 保留 + 6 新增），配置层的 12 项契约参数键另立 `CONTRACT_KEYS`；第 13 项 `endingBestChain` 为派生量（`clueCount × 3`），**不设独立数值、不进配置与 `cs.difficulty`**，由 `game.js` 现算，仅在 `DERIVED_KEYS` 声明。采纳。

制作人已独立复跑 `js/difficulty.js` 终版：`node --check` SYNTAX_OK；12 组派生值与 QA `EXPECT_MATRIX` 逐项一致；`basic` 三夜 ≡ D₀(n)；`IDS / DEFAULT_TIER_ID / normalize / paramsFor / apply / validateConfig` 齐备。**该文件定版**。

## 10. 事实纠正 · RNG 消费序列与复现主键（阻断级，QA 必读）

架构 §3.6 / §7.2-2 有三处陈述：「`shuffle(...).slice(...)` 不额外消耗 RNG」「红鲱鱼分支在客人数据生成完毕之后才消耗主 RNG」「`clueCount` 改变不影响 RNG 消耗序列」。**三处均与实测不符，作废**，以设计案 §6.4 / R1 为准。

制作人独立复算（`node -e` 直调 `Director.generate('SEED', n)`）：

```
night=1 lamps=6 clueCount=1 redHerring=false impostorId=g1 客人=裴照/苏晚/顾长风 物证=baggage:刀匣
night=2 lamps=5 clueCount=1 redHerring=true  impostorId=g2 客人=顾长风/苏晚/谢无咎 物证=companion:独行
night=3 lamps=5 clueCount=2 redHerring=true  impostorId=g1 客人=程鹤/云阿罗/阿檀   物证=hour:一更|origin:北坡
```

源码依据（`js/director.js`）：

- `L75` `new C.RNG(seed + '|night' + night + '|try' + attempt)` —— **种子本身就含 `night`**；
- `L80–88` `clueTpls = rng.shuffle(...).slice(0, diff.clueCount)` 之后，每个物证模板都调 `rng.pick(topic.values)`，`clueCount` 增大 → **多消耗一次主 RNG**；
- `L111–114` 红鲱鱼分支位于 `picks.map()` **内部**（客人生成循环里），`makeSurface(rng, ...)` 直接消耗**主 RNG**，不是「之后」；
- `L133–141` 红鲱鱼二次分配亦在客人生成之后但对同一 `rng` 流生效。

**裁决 J（复现主键）**：由 `(seed, night)` 扩为 **`(seed, night, tier)`**。

| 场景 | 规则 |
|---|---|
| `basic`（默认） | 参数 ≡ `D₀(n)` ⇒ 旧链接 / 旧存档 / 200 组种子自检**逐字节复现** |
| 其余三档 | 分享与复跑链接**必须带** `?difficulty=<id>`；`shareText()` 追加「难度：\<中文名\>」一行 |
| `?seed=X&night=N` 不带 `difficulty` | 回落 `basic`，与 v1.1.0 一致 |
| **禁止** | 把 `tierId` 拼进 RNG 盐串 / seed 来「绕开」差异——会作废全部既有链接（设计案 R1 已列为不可砍项） |

**给 QA 的直接后果（必须改断言，不得沿用旧期望）**：

1. **不得**写「同 seed 跨档案件相同」这类通过断言；正确断言是「同 `(seed, night, tier)` + 同动作序列 → 逐位复现」（D-30 / D-31 现文案正确，保留）。
2. **应新增正向断言**：同 seed、同 night、不同 tier → 案件（客人 / 物证 / 无相 id）**确实不同**，证明档位真实生效，而非仅换了个标签。
3. `D-23` 非法 id 用例里的 URL 键 **`?tier=` 全部改为 `?difficulty=`**；8 类非法值样本保留。
4. `D-12` 中 `EXPECT.TIER[最难] / [新手]` 的占位键名改为裁决 B 的四档 id。
5. `?guide=1` 必须固定 `basic` + 第 1 夜并**忽略** `?difficulty`，否则引导验收写死的 `6 / 6 盏` 基线整片 FAIL。

## 12. 撤销误执行版本 · 与只读观测通道（阻断级补裁）

### 12.1 撤销 `docs/难度分级-设计案-v1.md` 的 13:07 六字段重写版

**事实**：design-director 在 13:07 把设计案重写为「6 字段 × 12 组 = 72 终值 / `novice,easy,normal,hard` / `?tier=` / `App.session.difficulty` / `不在 cs.difficulty 新增任何字段`」，并注明是「依制作人《参数字段命名与硬约束》裁决」。

**裁决：该版本作废，不得作为任何实施或验收依据。**

- 它执行的是我在设计案落盘前发出的**旧裁决**，那条裁决已在**本单 §1「关于我自己先前裁决的修订」中明确作废**（当时只搜了 `cs.difficulty.*` 动态读取，漏了硬编码字面量这一消费点）；
- 更关键的**需求判据**：用户原话要求「敌人强度、资源数量、时间限制、**容错率**等」。六字段版只有 `lamps/clueCount/evadeBoost/redHerring/allowFlee/temperature`，把 `chainMinForFullCredit`（证据链容错）、`endingBestTrust`（评级门槛）、`trustMaskBelow/tensionLeaveAt/fleeSuspicionAt`（NPC 对抗强度）、`suspicionGainScale`（疑心累积）全部删除 → **「容错率」维度无对应物，属需求缺口**，不能因为改动面小就接受；
- 13 项版已由 QA 两个独立判定工具写死期望值并验证（`difficulty-matrix-oracle.cjs` 12/12 矩阵 + 12/12 边界；`difficulty-oracle-selftest.cjs` 23/23），且已派出 4 张实施单，推翻的代价与风险都远大于恢复。

**恢复数据源（数值未丢失）**：`tools/qa/difficulty-matrix-oracle.cjs` 顶部常量完整保存 `TIER_IDS / DEFAULT_TIER / D0 / T(13 项契约) / RANGE / EXPECT_MATRIX(12 组)`；字段名与口径见本单 §3 / §11；§5.2 公式与 §5.3 派生表的 prose 由设计侧据其 13:01 原稿恢复。恢复后版本标 **v1.1，取代：v1 六字段重写版（作废）**。

### 12.2 裁决 K · 13 项参数的只读观测通道

QA 的 D-10 指出真缺口：`Game.snapshot()`（`sandeng.state.v1`）按硬约束 G3 **结构不改**，因此 `SANDENG_API.getState()` 不含难度字段，三通道复算缺「状态」一条。**裁决**：

| 通道 | 落地方式 | 是否改 `snapshot()` |
|---|---|---|
| 状态通道 | **`SANDENG_API.getDifficulty()`**：返回 `{ tier, configId, params }` 的**深拷贝**，params 含运行期 13 字段；只读、纯函数、不缓存、不写全局 | **否**（新增 API 方法，不动 snapshot） |
| DOM 通道 | 封面四档控件带 `data-tier` + `aria-checked`；顶栏 `#tb-tier` 带 `data-difficulty-tier` | 否 |
| 存档通道 | `sandeng.save.v2.session.difficultyTier`（字符串 id） | 否 |

- `getDifficulty()` 必须返回**拷贝**而非 `cs.difficulty` 引用，防止外部调用篡改内部状态；
- `SANDENG_API.version` **保持 `'1.0.0'` 不变**（API 契约版本与产品发布版本是两个维度，借机改会破坏既有 `browser-smoke.cjs` 断言），只在 `docs/交付清单.md` 如实登记新增方法；
- 三通道只用于取**实际值**；期望值一律来自 QA 脚本顶部写死常量（判据①），不得反读这三通道生成期望值。
